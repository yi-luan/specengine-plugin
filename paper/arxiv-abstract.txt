Large language model (LLM) coding agents fill gaps in under-specified requirements with unstated assumptions, and when tests and specification conflict they may pass the tests anyway. Specification-driven development (SDD) tools write a specification before coding, but the agent still derives the tests on its own, and both remain editable while the code is written. SpecEngine applies stepwise refinement: a requirement becomes a rule matrix whose fields form a Hoare triple, then Gherkin bound to step definitions through a thin driver interface, then code. Every open boundary becomes a multiple-choice question for a human; a dependency-free script freezes the specification, step sentences, and driver interface during implementation; and a per-module lock lets later audits detect edits. We implement SpecEngine as a Claude Code plugin and evaluate it in a case study and a public benchmark of four requirements under three conditions (no SDD tool, GitHub Spec Kit, SpecEngine), scored by hidden acceptance tests. With strong models, both SDD tools clearly beat the baseline, which invented every failure code, and tied with each other. With a weak model, Spec Kit asked one question on an order state machine and scored no better than the baseline (20/32), while SpecEngine, which queues open boundaries by procedure, kept full marks (32/32, 38/38). On event-driven services built solo and by three-agent teams, SpecEngine scored 36/36 in all four settings, though neither tool checks contracts between services. The lock detected all 11 tampered specifications; fault injection showed that dropped rules and scenarios are caught by script only in SpecEngine, and that emptied step bodies escape every condition. Cells hold one or two runs, stakeholders were simulated from answer sheets, and the freeze detects rather than prevents deliberate edits.
