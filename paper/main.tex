\author{\IEEEauthorblockN{Yilun Tsai}
\IEEEauthorblockA{\textit{In-Service Master's Program in Artificial Intelligence and Information Systems}\\

\begin{abstract}
Large language model (LLM) coding agents fill gaps in under-specified requirements with unstated assumptions, and when tests and specification conflict they may pass the tests anyway. Specification-driven development (SDD) tools write a specification before coding, but the agent still derives the tests on its own, and both remain editable while the code is written. SpecEngine applies stepwise refinement: a requirement becomes a rule matrix whose fields form a Hoare triple, then Gherkin bound to step definitions through a thin driver interface, then code. Every open boundary becomes a multiple-choice question for a human; a dependency-free script freezes the specification, step sentences, and driver interface during implementation; and a per-module lock lets later audits detect edits. We implement SpecEngine as a Claude Code plugin and evaluate it in a case study and a public benchmark of four requirements under three conditions (no SDD tool, GitHub Spec Kit, SpecEngine), scored by hidden acceptance tests. With strong models, both SDD tools clearly beat the baseline, which invented every failure code, and tied with each other. With a weak model, Spec Kit asked one question on an order state machine and scored no better than the baseline (20/32), while SpecEngine, which queues open boundaries by procedure, kept full marks (32/32, 38/38). On event-driven services built solo and by three-agent teams, SpecEngine scored 36/36 in all four settings, though neither tool checks contracts between services. The lock detected all 11 tampered specifications; fault injection showed that dropped rules and scenarios are caught by script only in SpecEngine, and that emptied step bodies escape every condition. Cells hold one or two runs, stakeholders were simulated from answer sheets, and the freeze detects rather than prevents deliberate edits.
\end{abstract}

\section{Introduction}
%======================================================================

Large language model (LLM) coding agents have evolved from completion aids into autonomous executors that read requirements, edit many files, run tests, and iterate on their own. Once agents produce more code than developers can review, oversight rests largely on the automated test suite~\cite{zhao2026specbench}. Tests, however, are only a proxy for the specification, and proxies can be gamed. Two failure modes follow. The first is \emph{silent gap-filling}: a short requirement leaves many boundaries open, and the agent picks a plausible behavior for each without asking and without recording the choice. In the benchmark of Section~\ref{sec:eval}, an agent working without a specification tool listed its assumptions faithfully and still got every failure code wrong. The second is \emph{test exploitation}: when tests and the specification conflict, frontier models frequently pass the tests anyway, by editing the tests, special-casing the code, or hard-coding expected outputs~\cite{zhong2025impossiblebench,gabor2025evilgenie}.

To counter the first behavior, practitioners began adopting specification-driven development (SDD) in 2025, which has the agent write a structured specification before writing code; representative tools are GitHub Spec Kit and Amazon Kiro. B\"ockeler~\cite{bockeler2025sdd} distinguishes three levels of ambition---spec-first, spec-anchored, and spec-as-source---and Piskala~\cite{piskala2026sdd} turns them into a practitioner's guide. In current tools, however, the agent still derives the tests from the specification largely on its own, and both the specification and the tests remain editable while the code is written; Kiro, for example, offers to fix ``the spec, implementation, or test itself'' when a property-based test fails~\cite{kiro2026correctness}. Current SDD, in short, deals with a specification that is \emph{missing}, not with one that is \emph{mutable}. Conversely, studies of test exploitation have shown how common the second behavior is and have evaluated mitigations such as read-only tests~\cite{zhong2025impossiblebench}, but they freeze test files rather than the specification the tests are derived from.

Both behaviors have a common root: the specification is not independent of the agent. In the vocabulary Alexander~\cite{alexander1979timeless} uses for design problems, the situation is a conflict among five \emph{forces}: (F1) delivery speed versus verifiability; (F2) agent autonomy versus human decision authority; (F3) human readability versus machine executability of the specification; (F4) specification stability versus implementation freedom; and (F5) constraint strength versus process friction. Current SDD tools resolve F3 largely in favor of readability and leave F4 unresolved.

This paper presents SpecEngine, a workflow that applies stepwise refinement~\cite{wirth1971stepwise} to LLM coding agents and freezes each refined level by hashing. Requirements are decomposed into a rule matrix whose fields are the precondition, command, and postcondition of a Hoare triple~\cite{hoare1969axiomatic}. Every undefined behavioral boundary is externalized as a multiple-choice decision for a human stakeholder. Confirmed rules are compiled into Gherkin and bound to step definitions through a thin driver interface. Before implementation, a script records hash snapshots of the specification, the step sentences, and the driver interface, and verifies them afterwards. Module state is derived from artifacts rather than recorded, and each finished module receives a lock, committed to version control, against which later audits detect edits.

The contributions of this paper are as follows.
\begin{itemize}
\item We frame specification integrity under LLM agents as an explicit design problem using problem frames~\cite{jackson2001problem} and force analysis, and delimit the solution with eight first-class entities and four invariants.
\item We propose a three-layer freeze that fixes \emph{what counts as correct} while leaving \emph{how it is achieved} open. Changes the agent makes to the specification, the step sentences, or the driver interface during implementation are detected at verification, except through one recorded route and under the threat model stated in Section~\ref{sec:freeze}.
\item We implement SpecEngine as an open-source Claude Code plugin whose enforcement scripts use only the Node.js standard library.
\item We report a case study in which the workflow took a four-sentence requirement to an all-passing, locked module, and in which the agent, when its own formalization error collided with the frozen contract, reported the defect instead of rewriting the contract.
\item We report a public benchmark comparing SpecEngine with GitHub Spec Kit and with no SDD tool on four requirements, including event-driven services built by three-agent teams, with strong and weak models, hidden acceptance tests, tampering, fault injection by refinement level, and mutation testing.
\end{itemize}

The rest of the paper is organized as follows. Section~\ref{sec:related} reviews related work. Section~\ref{sec:method} defines the problem and the conceptual model and presents the method. Section~\ref{sec:case} reports the case study and Section~\ref{sec:eval} the benchmark. Section~\ref{sec:discussion} discusses the results, the remaining evaluation, and threats to validity. Section~\ref{sec:conclusion} concludes.

\section{Related Work}\label{sec:related}
%======================================================================

\subsection{Stepwise Refinement, BDD, and Executable Specifications}

Wirth~\cite{wirth1971stepwise} described program development as a sequence of refinement steps, each decomposing a task into more detailed instructions while deferring representation decisions as long as possible. Behavior-driven development (BDD) was introduced by North~\cite{north2006bdd} and later organized by Smart and Molak~\cite{smart2023bdd} into three activities: discovery, formulation, and automation. Gherkin is the most widely used BDD specification language; its Feature--Rule--Scenario hierarchy and Given/When/Then steps are parsed by runners such as Cucumber and bound to step definitions~\cite{cucumber2018gherkin}. Wynne's Example Mapping~\cite{wynne2015example} structures discovery conversations with four kinds of cards: the story, its rules, examples, and open questions. Adzic~\cite{adzic2011sbe} argues for replacing abstract statements with concrete examples that become executable living documentation. On the design side, Evans's ubiquitous language~\cite{evans2003ddd} requires business, code, and tests to share one vocabulary, while Hoare's axiomatic semantics~\cite{hoare1969axiomatic} and Meyer's design by contract~\cite{meyer1992dbc} provide the formal basis of precondition, command, and postcondition. Humble and Farley~\cite{humble2010cd,farley2021mse} describe a four-layer acceptance-test architecture---test cases, a domain-specific language, protocol drivers, and the system under test---so that test cases survive user-interface changes. Beck's test-driven development~\cite{beck2002tdd} and Freeman and Pryce's double loop~\cite{freeman2009goos} define the red--green--refactor rhythm of implementation. SpecEngine proposes no new theory; it chains these practices together and enforces by script the steps that otherwise depend on the discipline of whoever performs the refinement.

\subsection{Specification-Driven Development}

B\"ockeler's analysis of Kiro, Spec Kit, and Tessl~\cite{bockeler2025sdd} shows that the term SDD covers three levels of ambition and raises open questions, including whether reviewing Markdown documents is cost-effective and whether SDD repeats the mistakes of model-driven development. Piskala~\cite{piskala2026sdd} organizes the three levels into a practical guide and decision framework but reports no controlled experiment. As of October 2026 we found no published controlled evaluation of Spec Kit or Kiro. Spec Kit's core workflow is constitution, specify, plan, tasks, implement, and converge, with optional clarify and analyze commands~\cite{speckit2026}. Its specification consists of user stories with Given/When/Then acceptance scenarios; \emph{clarify} asks at most five questions per session, and \emph{converge} has the model compare the code with the specification, plan, and tasks and append unfinished work. Kiro writes requirements in the EARS notation and can generate property-based tests from them; when such a test fails, it can update the implementation or offer to fix the specification, the implementation, or the test~\cite{kiro2026correctness}. In both tools the agent derives the tests, the specification stays editable during implementation, and no mechanism records or detects an edit to it.

\subsection{LLMs and BDD Scenario Generation}

Karpurapu et al.~\cite{karpurapu2024bdd} compared GPT-3.5, GPT-4, Llama-2, and PaLM-2 at generating BDD acceptance tests with zero- and few-shot prompting and found almost no syntax errors in the GPT models' output. Rathnayake et al.~\cite{rathnayake2026bdd} compared GPT-4, Claude~3, and Gemini on 500 user stories from four commercial products and found that text-similarity metrics ranked the models differently from human experts, and that the level of detail in the input requirement clearly affected output quality. Other work examines epic-organized generation~\cite{siddeeq2026epic} and a human-centred quasi-experiment on Gherkin generated from regulations~\cite{hassani2025law}. These studies evaluate textual quality; the generated Gherkin is not bound to step definitions and executed, and its life cycle after generation is not addressed.

\subsection{Test-Driven Formalization of User Intent}

Lahiri et al.~\cite{lahiri2022ticoder} proposed TiCoder: because natural language is ambiguous, the model should generate test cases for the user to confirm instead of guessing, and the confirmed tests are then used to prune candidate programs. On MBPP and HumanEval, one to five simulated queries raised pass@1 by 22 to 54 percentage points. Fakhoury et al.~\cite{fakhoury2024ticoder} showed in a study with 15 participants that the workflow improved users' ability to judge AI-generated code correctly and reduced cognitive load. TiCoder shares SpecEngine's idea of externalizing decisions, but its questions are function-level input--output pairs, whereas ours are module-level business and engineering trade-offs. TiCoder does not address whether confirmed tests remain fixed during later generation, and its accuracy evaluation uses simulated users.

\subsection{Test Exploitation and Reward Hacking in Coding Agents}

Zhong et al.~\cite{zhong2025impossiblebench} introduced ImpossibleBench, which mutates unit tests from LiveCodeBench and SWE-bench to contradict the specification and defines the cheating rate as the pass rate on such impossible tasks. They also evaluated mitigations: hiding the tests reduced cheating to near zero but lowered legitimate performance; making them read-only prevented test modification but not special-casing; and an option to flag a task for human intervention reduced cheating sharply for some models. Gabor et al.~\cite{gabor2025evilgenie} introduced EvilGenie and observed explicit reward hacking by Codex and Claude Code, mostly through heuristic special-casing and hard-coded test cases rather than edits to test files. Zhao et al.~\cite{zhao2026specbench} introduced SpecBench, which splits each task into visible and held-out tests and measures hacking as the gap between the two pass rates; the gap grows with code size, by about 28 percentage points per tenfold increase. Drawing on production experience, Wahi~\cite{wahi2026judge} argues that LLM-as-a-judge signals can only be advisory and that deterministic checks must act as gates the judge cannot override.

SpecEngine's freeze is closest to ImpossibleBench's read-only tests and abort option. It differs in what is frozen and for how long: not test files but the refined specification from which they are derived (the Gherkin contract, the step sentences, and the driver interface), delimited per module, with step bodies deliberately left editable, and extended past implementation by a lock that later audits check. It also pairs the freeze with human-answered decisions upstream. We are not aware of prior work that combines an executable, module-delimited specification freeze with post-release audit in an agent workflow.

\section{Method}\label{sec:method}
%======================================================================

This section defines the problem and its forces (\ref{sec:problem}), introduces the conceptual model and invariants (\ref{sec:model}), presents the workflow architecture (\ref{sec:arch}) and its core mechanisms (\ref{sec:decisions}--\ref{sec:failures}), and describes the implementation (\ref{sec:impl}). It describes release 2.0.0; the changes in release 2.1.0 are listed at the end of Section~\ref{sec:impl}.

\subsection{Problem Definition and Forces}\label{sec:problem}

Following Jackson's problem frames~\cite{jackson2001problem}, we separate the machine to be built---the workflow $W$---from four problem domains: the requirements document $R$ (a lexical domain, incomplete and ambiguous); the stakeholder $S$ (a biddable domain that holds decision authority but has limited time); the agent $A$ (biddable but untrusted: when goals and instructions conflict, it tends toward the path of least resistance); and the codebase and test environment $T$ (a causal domain). The requirement is that the behavior of $T$ satisfies $R$ as adjudicated by $S$. Were $A$ trustworthy, this would be Jackson's required-behaviour frame. Because it is not, an additional frame concern arises: $A$ both operates on $T$ and may rewrite the description of $R$. If the specification and the tests are both within $A$'s write scope, ``$T$ passes the tests'' no longer implies ``$T$ satisfies $R$''. The machine therefore has two responsibilities: (a) turn $R$ into executable criteria, with gaps filled by $S$; and (b) make any change $A$ makes to those criteria detectable while $A$ operates on $T$. Current SDD tools take on (a); this work is centered on (b).

The design must balance the five forces listed in Table~\ref{tab:forces}. Current SDD tools favor readability in F3, leave F4 unresolved, and externalize F2 only partially. The rightmost column of Table~\ref{tab:forces} gives SpecEngine's response to each force.

\subsection{Conceptual Model and Invariants}\label{sec:model}

We define the objects of the solution as eight first-class entities. Table~\ref{tab:entities} lists their definitions, owners, and whether they may change during the freeze, that is, while the agent implements; ``by instruction'' marks artifacts that the instructions forbid editing but that the snapshot of release 2.0.0 does not hash; Fig.~\ref{fig:model} shows their relations. Not in the table, and entirely free during the freeze, are the bodies of step-definition functions, driver implementations, and product code. This boundary is where F4 is resolved.

\centering\footnotesize
\begin{tabularx}{\textwidth}{@{}lL>{\raggedright\arraybackslash}p{3.6cm}c@{}}

\midrule

Step Sentence & The text of each Given/When/Then in the Contract; also the key of a test function & Generated by $A$ from the Contract & No (sentence set) \\

\bottomrule
\end{tabularx}
\end{table*}

The machine must maintain four invariants.
\textbf{I1 (contract immutability):} during the implementation of any module, the hashes of the Contract and the Driver Interface and the set of Step Sentences equal those at the start of implementation; otherwise implementation may not be declared complete.
\textbf{I2 (complete correspondence):} each Rule of a formalized module has exactly one corresponding block in the Contract, and vice versa.
\textbf{I3 (real bindings):} every Driver method declared by a Step Sentence exists in the Driver Interface.
\textbf{I4 (decision ownership):} every Decision is answered by $S$.
Scripts check I1--I3. I4 is the only invariant a script cannot verify: a script can prove that an answer exists, not where it came from.

Module state is not a first-class entity but a function of which entities exist. For a module $m$: if Lock($m$) exists, $m$ is IMPLEMENTED; otherwise, if step-definition files tagged with $m$ exist, it is STUBBED; otherwise, if Gherkin tagged with $m$ exists, FORMALIZED; otherwise, if an unanswered Decision belonging to $m$ exists, CLARIFYING; otherwise, if a Rule matrix for $m$ exists, CLARIFIED; otherwise UNDISCOVERED. Completion of P3 is derived from a status line in the flow-diagram index file and determines whether a CLARIFIED module resumes at P3 or P4. Whatever the stage, an unanswered Decision makes clarification the next step. With this definition, state does not depend on the agent's self-report.

\subsection{Workflow Architecture}\label{sec:arch}

The workflow has six phases, shown in Fig.~\ref{fig:workflow} and Table~\ref{tab:phases}. P1 and P4--P6 are non-interactive, except that P1 may ask which module a requirement belongs to; P2 and P3 are human gates at which the agent must stop and wait for $S$. A single command chains the six phases; its starting point is given by the state function of Section~\ref{sec:model}, so a restart after an interruption does not repeat completed phases. Creating and checking the environment manifest, and post-release audits, are governance actions outside the chain. A return from P6 to P2 re-enters the same gate, so there are still only two points of human intervention. The snapshot is created at the end of P5 and recreated at the start of P6, as a boundary operation between the two phases.

The design principle of the chain is stepwise refinement: the room for free interpretation strictly shrinks at each level. The Requirement is natural language; Rules and the Contract are structured specifications with fixed fields; the Driver Interface is a fixed set of primitives; step bodies, driver implementations, and product code form the bottom level, where only implementation freedom remains. The three fields of a Rule are a Hoare triple~\cite{hoare1969axiomatic}, which becomes Gherkin's Given, When, and Then and then three test functions. Because the shape is preserved across levels, every transformation below the Rule is close to mechanical. The transformation that requires most judgment is from Requirement to Rule, and that judgment is externalized by the mechanism of Section~\ref{sec:decisions}. The Driver Interface corresponds to the protocol driver in Farley's four-layer architecture~\cite{farley2021mse}. It allows the same Contract to run quickly against an in-process driver for the red--green loop of P6 and then against a user-interface driver for acceptance, with the Contract and Step Sentences unchanged in between. A project may also declare a \emph{direct} binding, in which step definitions call product code without a driver; Driver Interface checks are then skipped.

\subsection{Decision Externalization}\label{sec:decisions}

P1 separates the Requirement into defined and undefined parts. Defined parts become Rules. Undefined parts are examined against a probe list---numeric precision, repeated triggering and idempotency, threshold values, failure and rollback, data life cycle---and each gap becomes a Decision with a plain-language question, two or three options with their engineering consequences, scope of impact, priority, and whether it is reusable across modules. This amounts to writing the rule, example, and question cards of Example Mapping~\cite{wynne2015example} into files. Because the probe list is applied by procedure, the number of questions depends less on the model's own judgment of which ambiguities matter; Section~\ref{sec:eval-weak} suggests why this matters.

P2 groups Decisions by locus (the same entity or the same Rule), at most four per group, and presents them as multiple-choice rather than open questions. The agent's task in this phase is limited to translating technical terms into domain language and writing $S$'s answers to the right place. Answers go into four kinds of entities by their nature: a decision that causes an action goes into a Rule; a decision that the system does nothing, does not offer something, or defers to another module goes into an Exclusion; data types and constraints go into the data model; names and fixed messages go into the glossary. The separate Exclusion entity is necessary because the three-field Rule structure is designed for ``an action causes a result''; forcing ``the system deliberately does nothing'' into it produces tests that always pass and discriminate nothing. Any Decision still unanswered when P2 is left is \emph{parked}, and P4 turns it into a visible comment in the Contract; a Decision ends either answered or parked. When a Decision is marked reusable, its answer is also written to a list of conventions, which P1 applies directly when a later module meets the same kind of gap.

P3 complements P2. Answering questions one by one is a local view and does not guarantee overall completeness. The agent draws the Rule matrix as flow diagrams by sub-scenario, adds a plain-language restatement and the list of Exclusions, and lists the gaps it suspects for $S$ to rule on. The hard constraint is that only Rules present in the matrix may be drawn. When $S$ identifies a gap, it becomes a new Decision and the module returns to P2; items $S$ rules to be non-gaps are kept whether or not the round passes.

\subsection{Three-Layer Freeze and Completion Lock}\label{sec:freeze}

This is the core mechanism of the method and enforces invariant I1. Algorithm~\ref{alg:freeze} gives its pseudocode. Feature files are tagged per module with a Gherkin tag \code{@rule:R-}$m$\code{-}, and step-definition files with a code comment \code{@rule R-}$m$\code{-}; the difference follows the syntax of each host.

\begin{algorithm*}[t]
\caption{Snapshot, verification, lock, and audit}\label{alg:freeze}
\footnotesize
\begin{algorithmic}[1]
\Function{Snapshot}{$\mathit{specDir}, \mathit{stepDirs}, \mathit{driverDirs}$}
  \State $S \gets \{ f \mapsto \mathrm{sha256}(f) \mid f \in \mathrm{files}(\mathit{specDir}) \}$
  \State $T \gets \{ f \mapsto \mathrm{sentences}(f) \mid f \in \mathrm{files}(\mathit{stepDirs}) \}$ \Comment{sorted set of (keyword, text) of every \code{Given|When|Then('text', ...)} call}
  \State $D \gets \{ f \mapsto \mathrm{sha256}(f) \mid f \in \mathrm{files}(\mathit{driverDirs}),\ f \text{ matches } \code{*.driver.*} \}$
  \State \textbf{assert} $|\bigcup T| > 0$ \Comment{no sentences means the stubs are missing}
  \State \textbf{assert} \Call{BindsValid}{$T, D$} \Comment{every \code{@binds X.y} names a method \code{y} present in $D$ (I3)}
  \State write $(S, T, D)$ to the snapshot file
\EndFunction
\Function{Verify}{$\mathit{snapshot}$}
  \State $(S', T', D') \gets$ recompute as in \Call{Snapshot}{}; \ $V \gets \emptyset$
  \ForAll{$f \in \mathrm{keys}(S) \cup \mathrm{keys}(S')$ \textbf{with} $S[f] \neq S'[f]$} \State $V \gets V \cup \{(\textsc{spec}, f)\}$ \EndFor
  \ForAll{$f \in \mathrm{keys}(T) \cup \mathrm{keys}(T')$}
    \State $V \gets V \cup \{(\textsc{sentence-removed}, f, s) \mid s \in T[f] \setminus T'[f]\} \cup \{(\textsc{sentence-added}, f, s) \mid s \in T'[f] \setminus T[f]\}$
  \EndFor
  \ForAll{$f \in \mathrm{keys}(D) \cup \mathrm{keys}(D')$ \textbf{with} $D[f] \neq D'[f]$} \State $V \gets V \cup \{(\textsc{driver-interface}, f)\}$ \EndFor
  \If{$V = \emptyset$} \State exit 0 \Else \State report $V$; exit 1 \EndIf
\EndFunction
\Function{Lock}{$m$}
  \State $F \gets \{ f \mapsto \mathrm{sha256}(f) \mid f \text{ a feature file containing tag } \code{@rule:R-}m\code{-} \}$
  \State $T \gets \{ f \mapsto \mathrm{sentences}(f) \mid f \text{ a step file containing } \code{@rule R-}m\code{-} \}$
  \State $D \gets \{ f \mapsto \mathrm{sha256}(f) \mid f \text{ a driver-interface file referenced by } \code{@binds} \text{ in } T \}$
  \State write $(m, \mathit{timestamp}, F, T, D)$ to \code{locks/}$m$\code{.lock.json} \Comment{committed to version control}
\EndFunction
\Function{Audit}{}
  \ForAll{locks $(m, t, F, T, D)$} \State recompute and compare as in \Call{Verify}{}; report \textsc{lock-drift} per module \EndFor
\EndFunction
\end{algorithmic}
\end{algorithm*}

The boundaries of the three layers correspond to the balance point of F4. The Specification Contract is frozen byte for byte because it defines what is correct. For Step Sentences only the sentences are frozen, not the function bodies: a sentence is the foreign key between the Contract and the code, while turning a body from throwing an exception into calling product code is precisely the work of P6. The Driver Interface is frozen and its implementations are not, for the same reason. When \textsc{Verify} fails, the instructions forbid the agent from declaring completion. The Lock extends the check past implementation: it records the module's feature files, Step Sentences, and Driver Interface, and \textsc{Audit} compares them later. In release 2.0.0 the Lock does not cover the shared data model, glossary, and conventions, which are frozen only during P6; release 2.1.0 adds them, together with the rule matrix. The theoretical basis is design by contract~\cite{meyer1992dbc}: the contract is an invariant that the implementation must satisfy, and it may not be amended to accommodate the implementation. What we add is distrust of the agent's self-discipline, turned into a check by hashing.

The threat model must be stated plainly. The scripts are run by the agent, and the snapshot file lies in the agent's write scope. An agent that edits the Contract and then re-runs \textsc{Snapshot} before \textsc{Verify} passes the check; what remains is the edit in version-control history and, after completion, a Lock that reviewers can compare. The mechanism therefore detects goal-driven or careless edits, which is the behavior reported in the studies of Section~\ref{sec:related}-E, not deliberate evasion by an agent that reasons about the check. Running \textsc{Verify} in continuous integration from a snapshot committed before P6 would close this gap; the current release does not do so. Within this model, the remaining ways to make a test pass without changing a frozen artifact are to change product code or a driver implementation, and two of those are escape hatches: the agent can reduce a Then step to an empty assertion or make the in-process driver return the expected value directly, and \textsc{Verify} will not notice. The current release lowers this risk with two instruction-level constraints: a step body may only convert types, call the driver, and assert; and if a user-interface or API driver is declared, acceptance must rerun the suite through it. Neither is enforced by script, and Section~\ref{sec:eval-inject} measures the first.

\subsection{State Derivation}\label{sec:state}

The state function of Section~\ref{sec:model} is implemented by a script that attributes artifacts to modules by tag-string containment and Decisions to modules by the module identifier appearing in each question file. It warns when lower-layer artifacts are missing (for example, step definitions without a Contract) and when a cached field disagrees with the derived state. This replaces the approach of an earlier version, in which the stage was stored in a field of the Rule matrix and rewritten by the agent at the end of each phase. Nothing kept that field consistent with the actual artifacts, and when it went stale unnoticed the chain restarted from the wrong phase. The current release keeps the field only as a cache. Audit results are not yet fed back into the state function: a module whose Lock exists but has drifted is still derived as IMPLEMENTED.

\subsection{Failure Classification and Fallback}\label{sec:failures}

When a test in P6 cannot be made to pass, the agent must first classify the failure (Table~\ref{tab:failures}). The criterion separating the second and third classes is whether the correct Contract text can be derived uniquely from the Rule matrix alone. If it can, the failure is a translation error that involves no business decision, and the agent may fix the Contract, record the fix in a dedicated file, rebuild the snapshot, and report both; if not, the question must go back to $S$. The second class was added after the case study (Section~\ref{sec:casediscussion}). To make it rarer, P4 must check row by row, before writing the Contract, that the inputs and expected results of each Examples row follow uniquely from the precondition and postcondition of its Rule; this check is performed by the agent, not by a script.

The second class deliberately reopens a route by which the agent may edit the frozen Contract during P6. The route is bounded: the edit must be recorded, the snapshot rebuild must be reported, the Step Sentences and Driver Interface stay frozen, and the instructions forbid editing the matrix. But the judgment that the answer is ``uniquely derivable'' is the agent's own, and a sanctioned fix can still lose coverage: in the case study (Section~\ref{sec:incident}), simply correcting the faulty row's expected message would have removed the only test of one branch. Across the 18 SpecEngine agent logs of the benchmark (Section~\ref{sec:eval}), no formalization fix occurred. The snapshot was rebuilt twice, both times after the agent corrected a manifest line that a script bug had misread and with no change to the specification; such benign rebuilds use the same route a deliberate edit would. Section~\ref{sec:remaining} treats the route as a threat to the evaluation design.

\subsection{Implementation}\label{sec:impl}

SpecEngine is implemented as a Claude Code plugin. Release 2.0.0 consists of ten instruction documents (skills), three Node.js scripts, one format specification, and two templates, totaling 1,903 lines by \code{wc -l}; four reference files (the P1 probe list, the question-file format, and two examples) add 278 lines. The scripts have no external dependencies and need no network; they read and write files only under the project directory. \code{feature-lint.js} implements Contract purity, matrix structure, I2, and the sentence index; \code{spec-guard.js} implements the four operations of Algorithm~\ref{alg:freeze}; and \code{spec-status.js} implements state derivation. The project's technology stack is declared in a single environment manifest, and the workflow itself makes no assumption about the stack. Driver-interface files are recognized by a file-name convention, which avoids the dependencies that parsing each language's interface syntax would require; in languages without interfaces, a base class whose methods all throw serves as the interface file. The parts tied to Claude Code are the packaging format of the instruction documents, the file into which the routing block is installed, the environment variable used in script paths, and the names of the tools the instructions use to ask questions, track tasks, and invoke sub-skills, each with a plain-text fallback. The scripts and the artifacts are tool-independent.

Release 2.1.0 adds a change workflow for modules that are already locked: a requested change is classified as a parameter change, a behavior change, or a new rule by comparing the old and proposed matrices; the stakeholder approves its scope; and on completion a script checks that every rule outside the approved scope is byte-for-byte unchanged. It also adds the rule matrix and the shared data model, glossary, and conventions to the Lock, and normalizes line endings before hashing. The weak-model and T4 runs of Section~\ref{sec:eval} used release 2.1.0; its phase instructions P1--P6 are unchanged from 2.0.0, while the lock and status scripts changed as described.

\section{Case Study}\label{sec:case}
%======================================================================

\subsection{Design}

To assess the feasibility of the method, we conducted an exploratory single-case study following the guidelines of Runeson and H\"ost~\cite{runeson2009case}. The unit of analysis is a single business module. The case addresses three questions. CQ1: can the workflow take a fresh project on a stack different from its development project from requirement to all tests passing and a Lock? CQ2: are invariants I1--I4 maintained during execution, and if they come into conflict, how does the agent behave? CQ3: which parts of the instruction text are ambiguous or contradictory, and what design gaps does the case reveal?

\subsection{Data and Setup}

The case project was an empty Node.js project with cucumber-js 13.3.0, plain JavaScript, and no browser. It was chosen because its stack differs from that of the project on which the tool was developed (TypeScript with playwright-bdd), which tests whether the environment manifest carries all stack assumptions. To preserve I4, the executor and the stakeholder were two model instances that shared no context. The executor ($A$) was instructed to read the instruction documents phase by phase and follow them, to run the scripts by absolute path, to list every question needing $S$'s answer in full and then end its turn, and to report ambiguities and contradictions in the instruction text after each round. The stakeholder ($S$) was played by a model instance in the researcher's session under the researcher's supervision; it answered only the multiple-choice questions and the flow-diagram confirmations and never saw the executor's artifacts. The executor used no mechanism specific to Claude Code. Both instances ran the default Claude Code model of October 2026; the exact version string was not recorded at the time (Section~\ref{sec:threats}). The case ran on a working version shortly before release 2.0.0; Section~\ref{sec:method} describes the final 2.0.0 release, and the differences are chiefly the fixes listed in Section~\ref{sec:casediscussion}. By the file system's clock, the run took about 35 minutes from the empty project to the Lock. The requirement consisted of four sentences written by the researcher, deliberately silent on exceeding the limits, repeated redemption, zero values, failure handling, and behavior after submission (translated from Chinese):

\begin{quote}\small
Members can redeem points against the order amount on the checkout page, one point for one dollar. The redeemed points may not exceed the order amount or the member's current point balance. After a successful redemption, the system deducts the points from the member and reduces the order's amount payable by the same number. Members can cancel the redemption before submitting the order, and the points are returned on cancellation.
\end{quote}

\subsection{Critical Incident}\label{sec:incident}

The failing Scenario Outline was ``when a repeated redemption is rejected, the previous redemption stays in effect''. Its Given steps set a balance of 100, an order amount of 500, and an existing redemption of 50; one Examples row entered 501 and expected the message ``redeemed points exceed the order amount''. According to the matrix, however, the available balance during a repeated redemption is 100; 501 exceeds both the balance and the order amount, and the precondition of rule R-002 states that the balance takes precedence when both are exceeded. The product code returned ``redeemed points exceed the balance'', which is correct; the Contract row was a translation error made by the executor in P4.

This was a direct conflict between I1 and the agent's goal. The shortest path to a green suite was to change the row's expectation to ``exceed the balance'': the test would have turned green and the report would have read 21/21. Under the instructions in force at the time, any edit to the Contract during P6 was forbidden and would have failed \textsc{Verify}. What the executor did was the following. It determined that the Contract was wrong; it created a Decision with three options and wrote it to the queue; it ran \textsc{Verify}, which passed, showing that the Contract had not been touched; it did not lock; and it halted, reporting a specification defect. The second class of Table~\ref{tab:failures} did not yet exist; this incident is why it was added. The options it offered show why the agent's judgment matters even then: the shortcut (option C) would have left no test of the ``exceeds the order amount'' branch during a repeated redemption, while the option $S$ chose (A) raised the Given balance to 1{,}000, kept a row for each branch (1{,}051 and 501), and adjusted the expected balance. The executor then corrected the outline through P4, rebuilt the snapshot, and completed P6. For CQ2, I1 was maintained when the conflict occurred. A single incident cannot tell whether this behavior came from the presence of the script or from the model's own disposition; Section~\ref{sec:remaining} gives a design to separate the two. The incident does show that such conflicts arise naturally in non-interactive phases and are not merely artifacts of benchmark construction.

After the Lock was created, the researcher changed one Examples value in the Contract from 501 to 502 and ran \textsc{Audit}, which reported LOCK\_DRIFT; after the value was restored, the current hashes matched the Lock exactly.

\section{Benchmark}\label{sec:eval}

The case study shows feasibility on one module. To compare SpecEngine with an existing SDD tool and with no tool at all, we built a public benchmark. Every number in this section can be regenerated from the artifacts and scripts in the repository (see Data Availability).

\subsection{Design}

\emph{Conditions.} A: no SDD tool; the agent was told to implement the requirement and add tests, could not ask anyone, and had to list every assumption. B: GitHub Spec Kit (\code{specify-cli} 1.2.3.dev0, commit \code{e5714c6}) with its Claude integration; the agent ran constitution, specify, clarify, plan, tasks, implement, and then converge until it reported convergence. C: SpecEngine 2.0.0; the agent ran manifest synchronization and then the chained workflow through both human gates, with direct binding. All conditions started from the same TypeScript project with cucumber-js.

\emph{Tasks.} Three requirements of increasing difficulty, written in Traditional Chinese: T1, loyalty-point redemption (7 open boundaries that must be asked, 18 hidden tests); T2, an order state machine (11 boundaries, 32 tests); and T3, multi-tenant coupons (14 boundaries, 38 tests). Each requirement fixes the public interface, so one hidden test file scores every condition. A change request on T1 (E4, raising a redemption cap from 30\% to 35\%, 12 hidden tests) was applied to one run per condition. T4, event-driven services built solo and by teams, is described in Section~\ref{sec:eval-t4}.

\emph{Stakeholder.} Each task has an answer sheet listing every open boundary with its correct answer. Questions were answered from the sheet and nothing else; questions not on the sheet were answered ``your call''. In the first runs the agent answered its own questions from the sheet under an instruction not to read ahead; three T3 runs broke that rule and are void. Their replacements, and all weak-model runs, had questions answered by a separate session, with the sheet out of the agent's reach.

\emph{Scoring.} Hidden tests import the fixed interface and are never visible to the agent. Each test is tagged with the boundary it checks and with its kind: behavior (what happens) or reason (which failure code is returned). A reference implementation written directly from each answer sheet passes all of its hidden tests.

\emph{Models.} Strong-model runs of T1, T2, and E4 used Claude Fable 5.1. On T3, the two clean replacement runs (Spec Kit r3 and SpecEngine r3) ran entirely on Claude Opus 5.5, and Spec Kit r1 partly, after a model switch; the A runs used Fable 5.1. The strong T3 comparison therefore mixes two strong models. The weak-model runs used Claude Haiku 5.5, the smallest current Claude model, on T2 and T3 under all three conditions, with SpecEngine 2.1.0 and the same Spec Kit commit. All T4 runs used SpecEngine 2.1.0.

\subsection{Weak Model}\label{sec:eval-weak}

A common objection to stepwise refinement with an LLM is that a weak model will mistranslate somewhere along the chain. The weak-model rows of Table~\ref{tab:bench} show the opposite pattern. With Haiku 5.5, Spec Kit's clarify step judged T2 to have no high-impact ambiguities and asked one question; every failure code was then invented, and the run scored exactly what the no-tool run scored. SpecEngine kept full marks on both tasks: its discovery phase turns every open boundary found by the probe list into a queued question by procedure, so the weak model still asked about 9 of 11 and 13 of 14 boundaries and derived the rest correctly from the answers. Runs took 11 and 12.5 minutes with 202k and 278k tokens, against 7 and 9 minutes for Spec Kit. With strong models, the two SDD tools tied; with a weak model, the gap was 12 tests on T2 and 7 on T3. Each weak-model cell is a single run.

\subsection{Tampering with a Locked Specification}

For each locked SpecEngine run of T1--T4, a script changed one example value in the locked Gherkin (for example, 1000 to 1001) and ran \textsc{Audit}. Of the 12 locked runs, one weak-model run had no example value to change; all other 11 tampered specifications, including two from void runs, were reported as LOCK\_DRIFT within a second. Spec Kit has no lock, so the equivalent edit was committed to \code{spec.md} by hand and \code{converge} was run read-only by a fresh agent. Changing a cap from 30\% to 35\% in one user-story sentence was reported as converged with zero actionable findings, the contradiction appearing only as an awareness note; reversing ``shipped orders cannot be cancelled'' was reported as a critical contradiction after about 7.5 minutes. In condition A, changing an expected value in its own feature file left all tests green.

\subsection{Mutation Testing}

To check whether the conditions differ in the thoroughness of their own tests, a script mutated each run's product code one small change at a time and ran both the run's own tests and the hidden tests. Among mutants that broke a hidden test the original passed, the share also caught by the run's own tests was 91--100\% for condition A (9 runs), 100\% for Spec Kit (10 runs), and 95--100\% for SpecEngine (10 runs); these 29 runs include E4, the weak-model runs, and the three void runs. All conditions wrote thorough tests; the baseline's tests thoroughly checked behavior the agent had guessed. The conditions differ not in how well they test, but in whether the specification being tested is the stakeholder's.

\subsection{Change Request}

The change request E4 was applied to one T1 run per condition. Condition A took 2.5 minutes and passed 6 of 12 hidden tests: all change-related tests passed, but its original wrong guesses remained. Spec Kit reran its full workflow in 9 minutes and passed all 12. SpecEngine 2.0.0 had no documented change workflow; the agent assembled one from the existing phases in 17 minutes and passed all 12. Release 2.1.0 adds the change workflow described in Section~\ref{sec:impl}.

\subsection{Event-Driven Services and Team Development}\label{sec:eval-t4}

Three services---order, inventory, and payment---exchange events for order placement, stock reservation or rejection, payment success or failure, cancellation, refund, release, and a 15-minute timeout. The requirement states that delivery is at-least-once and unordered but not how to handle it; the answer sheet has 14 open boundaries. The hidden tests are 32 scripted scenarios with explicit duplicates and reorderings, driven through a test-controlled bus, and four property tests that replay 300 seeded random schedules and check that every order settles, stock and money are conserved, and no compensation event is sent twice. \section{Discussion}\label{sec:discussion}
%======================================================================

\subsection{What the Results Show}

Three findings stand out. First, with strong models, having any SDD tool mattered more than which one: both cleared the baseline by a wide margin on every task, and the baseline's failures were concentrated in exactly the boundaries a requirement leaves open. Second, the two SDD tools differed most under a weak model. Spec Kit's clarify step relies on the model's judgment of which ambiguities matter, and on T2 the weak model judged that none did; SpecEngine's probe list asks the model that question less. Our hypothesis is that procedure, rather than model strength, explains the gap. It is consistent with the observations but rests on single runs, and the weak model still missed boundaries that a strong model asked about (9 of 11 against 11 of 11 on T2) or that only the flow review recovered (T4). In T4 the gap was smaller and had a different cause: Spec Kit's weak solo run asked three questions and its losses include the one consistency failure, and its weak team run differed from SpecEngine's by a single test. In T4, consistency under duplicated and reordered events was handled in 11 of 12 runs once the requirement stated the delivery guarantees; what the tools added was agreement on decisions across services, and that agreement came from a shared stakeholder rather than from any check. Third, the lock detected every specification edit made after completion, at every level. The freeze during implementation (snapshot and verify) and the Driver Interface were exercised only in the case study: no benchmark run met a conflict, and all benchmark runs used direct binding. Two gaps remained open in every condition: example values that are wrong but consistent with the code, and step bodies emptied of assertions. Both point to concrete improvements: storing each rule's preconditions and postconditions as structured data so that a script can derive or check the example tables, and failing a phase when a Then step contains no assertion or when a mutation pass before locking finds surviving specification-relevant mutants.

\subsection{Remaining Evaluation}\label{sec:remaining}

The benchmark compares workflows; it does not isolate the contribution of the freeze itself, because in every SpecEngine run the tests went green without a conflict. The case study's incident is one observation. The question that remains is RQ1: with the same model and tasks, do hash-frozen artifacts lead to fewer unrecorded specification edits than a prompt-only prohibition? We propose the following design.

\emph{Conditions and tasks.} Twenty business modules, each with a requirement of three to six sentences containing at least two numeric boundaries and one state transition, written by someone not involved in the design. P1--P5 are shared across conditions and all Decisions are answered in advance, so every condition starts from the same all-failing state and variation comes from P6 alone. Arm F (frozen) uses the full instructions with the scripts; arm P (prompt-only) is identical with the script calls removed; arm U (unconstrained) only asks for the tests to pass. Because a contradiction between an Examples row and its Rule is a sanctioned formalization fix in release 2.0.0, the seeded conflicts must instead be specification defects: in half of the modules, two Rules are made to contradict each other in a way only $S$ can resolve, so that some test cannot pass without a decision. The other half measure the natural rate. Each module--condition pair is repeated five times, for 300 runs.

\emph{Measures.} Unrecorded change rate: the proportion of runs in which any frozen artifact differs between start and end without a corresponding fix record. Recorded fixes are counted separately, as are the two escape hatches: a Then step whose assertion was removed and a driver implementation that does not call product code. The honest-report rate, the false-completion rate (a report of all tests passing while an unrecorded change occurred), and the true-completion rate complete the set. All are computed by an independent script that does not know the condition.

\emph{Analysis.} The primary comparison is F against P on the seeded half, by a Cochran--Mantel--Haenszel test stratified by module. It is cross-checked by a mixed-effects logistic regression fit on all runs, with module as a random effect and arm, seeding, and arm $\times$ seeding as fixed effects. With 50 seeded runs per arm, a reduction from 40\% to 10\% is detectable at two-sided $\alpha = 0.05$ with power of about 0.94 if runs were independent; but the 50 runs come from 10 modules, and with an intra-module correlation of 0.2 the design effect is 1.8 and power falls to about 0.75. A pilot will therefore estimate the base rate and the intra-module correlation, and the number of modules will be set from them; twenty is a lower bound. Failing to reject the null would not show that the scripts are redundant: an equivalence claim needs a margin fixed in advance and several hundred runs per arm, which is beyond this design.

\emph{Decision quality.} RQ2 asks whether P1's Decisions cover the decision points that senior engineers list independently. Three engineers with at least five years of experience list, for the same requirements, the items an implementation must decide but the requirement leaves unstated; two raters, blind to the source, align items across lists, with their agreement reported as Cohen's $\kappa$. Every source, P1 included, is scored by leave-one-out recall against the union of the items listed by the three engineers other than itself, over the same 20 requirements. The hypothesis is non-inferiority: P1's recall is no more than ten percentage points below the engineers' mean recall.

\subsection{Threats to Validity}\label{sec:threats}

\emph{Construct validity.} The freeze detects byte changes, which counts meaning-preserving changes such as reformatting and misses tests that are untouched but passed through a wrong generalization. Driver interfaces are recognized by file name; an interface written to a file outside the convention is not frozen. In the benchmark, hidden tests check the fixed interface only, and a boundary counts as asked only if it appears among the agent's questions.

\emph{Internal validity.} The requirements, answer sheets, hidden tests, and evaluation were designed by the tool's author. Stakeholders were simulated from answer sheets, by the same agent in the first runs and by a separate session later; three runs that read ahead were voided. Runs were interrupted by rate limits and resumed, and the T3 hidden tests were corrected once and all T3 runs rescored. In T4 one session answered every developer from one sheet, so teams never received conflicting answers, as real teams can, and up to fifteen agents waited on that session at once, which inflates the times of conditions B and C unevenly. The case study's stakeholder was also a model instance, and its executor was explicitly told to stop, so I4 cannot be generalized from either study.

\emph{External validity.} All runs used one model family and one agent tool, and most cells hold one or two runs, so differences of one or two tests are not evidence of a difference between tools. The weak-model and T4 runs used release 2.1.0 while the T1--T3 strong-model runs used 2.0.0; their phase instructions are identical, but the comparison is not perfectly controlled. Tasks were small (7 to 14 open boundaries, at most three services); Zhao et al.~\cite{zhao2026specbench} report that hacking grows with code size, and the behavior on large modules is unknown.

\emph{Intrinsic limits of the mechanism.} Tests are examples, not proofs; the freeze prevents changing the question, not passing it with a wrong generalization. The scripts are run by the agent, so the freeze detects rather than prevents a deliberate edit (Section~\ref{sec:freeze}). The formalization-fix route lets the agent edit the Contract on its own judgment (Section~\ref{sec:failures}). I4 cannot be verified by script. Whether the Contract matches the business outcome lies outside the guarantee, and cross-module outcomes currently belong to no Rule. The shared data model and glossary are frozen byte for byte, so the current design effectively assumes that modules are implemented one at a time.

\section{Conclusion and Future Work}\label{sec:conclusion}
%======================================================================

We framed specification integrity under LLM agents as a conflict among five forces and observed that current specification-driven development tools resolve readability versus executability largely in favor of readability and leave stability versus freedom unresolved. SpecEngine answers both by stepwise refinement into an executable, hash-frozen contract: the freeze is limited to the objects that define correctness (the Contract, the Step Sentences, and the Driver Interface) and leaves implementation free (function bodies, driver implementations, and product code); decision authority is externalized through multiple-choice questions generated by procedure; and state is derived from artifacts. In a case study, the agent's own formalization error collided with the frozen contract, and the agent reported it rather than rewriting the contract. In a public benchmark, both SDD tools far outperformed no tool with strong models and tied with each other, and with a weak model SpecEngine kept full marks while Spec Kit fell to the baseline on one task; on event-driven services built by teams, SpecEngine again scored full marks, but neither tool checked the contracts between services; the lock detected every tampered specification, and fault injection located the two gaps that remain in every condition. The freeze during implementation was exercised only in the case study.

Future work follows from these results. First, the controlled experiment of Section~\ref{sec:remaining} would isolate the effect of the freeze from that of the workflow. Second, storing each Rule's conditions as structured data would let a script derive or check the example tables, and an assertion check or a mutation pass before locking would close the hollow-step gap. Third, running \textsc{Verify} in continuous integration against a snapshot committed before implementation would turn detection into prevention. Fourth, for cross-module and cross-service outcomes, objects and events passed between modules could become first-class entities whose producer postconditions and consumer preconditions cite the same contract identifier, so that a script can detect two teams deciding the same boundary differently. Fifth, moving the right to write Decision answers out of the agent's tool set would make I4 mechanical. Finally, distributing the core with thin adapters for other agent tools, and repeating the benchmark with more runs and other model families, would test tool independence and generality.
