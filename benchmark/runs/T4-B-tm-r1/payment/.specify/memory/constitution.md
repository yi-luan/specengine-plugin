# bench-points Constitution

## Core Principles

### I. Shared Contract Is Immutable
The event, status and service interface definitions in `src/events.ts` and the
integration entry `src/shop.ts` are the team-wide contract. They MUST NOT be
modified, renamed or extended by any individual service engineer. Every service
MUST implement its interface exactly as declared (factory function signature,
method names, return types). Rationale: three engineers integrate blind; a single
unauthorized change to the contract breaks everyone.

### II. Service Ownership & Isolation
Each engineer owns exactly one service file (`src/order.ts`, `src/inventory.ts`,
`src/payment.ts`) plus their own tests. An engineer MUST only edit their own
service file and their own tests; colleagues' files MUST be left untouched.
A service MUST keep its own in-memory state only, MUST NOT call or read another
service's state, and MUST communicate exclusively through the events it returns
from `handle`. Events the service does not care about MUST yield an empty array.
Rationale: isolation keeps parallel development safe and integration mechanical.

### III. Test-First With Executable Specifications (NON-NEGOTIABLE)
Behaviour is specified as Gherkin feature files run by cucumber-js. Scenarios and
step definitions MUST be written before the implementation and MUST fail first
(red), then the implementation makes them pass (green). `npm test` MUST run all
features and MUST be fully green before work is considered done. Because the other
services are empty shells during development, each engineer's tests MUST
fabricate the events other services would emit.

### IV. Event-Delivery Robustness
The bus guarantees at-least-once delivery, allows duplicates, and gives no
ordering guarantee. Every event handler MUST therefore be idempotent with respect
to duplicate deliveries and MUST tolerate out-of-order arrival without corrupting
state or emitting spurious events. Event ids generated by a service MUST be unique
system-wide. All amounts and quantities are integers; time values are ISO 8601
strings. Rationale: correctness under the real bus semantics is the core risk of
this system.

### V. Simplicity & Determinism
Everything runs in memory with no database, network or wall-clock access; time is
only what is passed in. Prefer the simplest structure that satisfies the spec
(YAGNI). Code MUST be deterministic so that tests are repeatable.

## Technology & Boundary Constraints

- Language: TypeScript (strict mode, ES2022, NodeNext modules) on Node.js.
- Test runner: cucumber-js (`@cucumber/cucumber`) via `npm test`, loaded with
  `tsx`; type checks via `npm run typecheck` (`tsc --noEmit`).
- Product code lives in `src/`; tests (feature files, step definitions, support
  code) live in `tests/`.
- No new runtime dependencies without an explicit, documented reason.
- Fixed, non-editable files: `src/events.ts`, `src/shop.ts`, colleagues' service
  files.

## Development Workflow & Quality Gates

- Workflow follows Spec Kit: constitution → specify → clarify → plan → tasks →
  implement → converge. Ambiguities in requirements MUST be raised to the
  requirements owner, never silently resolved; assumptions that are taken MUST be
  recorded.
- Gates before "done": (1) `npm run typecheck` passes; (2) `npm test` is green for
  every scenario; (3) only owned files were changed; (4) handlers are verified
  against duplicate and out-of-order delivery scenarios.

## Governance

This constitution supersedes any other practice in this repository. Amendments
require: a documented rationale, an updated version line, and a Sync Impact
Report. Versioning follows semantic versioning — MAJOR for incompatible
principle removals or redefinitions, MINOR for new or materially expanded
principles/sections, PATCH for wording clarifications. Every plan and
implementation review MUST check compliance with Principles I–V; any complexity
beyond the simplest solution MUST be justified in the plan.
