# Order Service (bench-points) Constitution

## Core Principles

### I. Spec-Driven, Test-First (NON-NEGOTIABLE)
Every behaviour of the order service MUST be written as a Gherkin scenario before product code
is written. Scenarios MUST fail (red) before implementation and pass (green) after. A feature is
"done" only when `npm test` runs its scenarios and every one of them passes. No behaviour that is
not covered by a scenario may be claimed as implemented.

Rationale: the integrator cannot see this engineer's reasoning; the executable spec is the only
shared truth across the three parallel services.

### II. Fixed Shared Contract
`src/events.ts` and `src/shop.ts` are the team contract and MUST NOT be modified or extended.
The order service MUST implement `OrderService` exactly as declared (method names, signatures,
`OrderStatus` values, `CommandResult` shape, event shapes) and MUST export
`createOrderService(): OrderService` from `src/order.ts`. Event `id` values generated by the
order service MUST be unique across the whole system (prefix them with the service name).

Rationale: three engineers integrate without seeing each other's code; any deviation from the
contract breaks integration silently.

### III. Service Isolation
The order service MUST keep only its own state in memory and MUST NOT import, call, or read
`src/inventory.ts` or `src/payment.ts`. All cross-service communication is via events returned
from `placeOrder`, `cancelOrder`, `tick`, and `handle`. The service MUST return an empty array
for event types it does not care about. No database, network, timers, or wall-clock reads: time
is only the ISO 8601 strings passed in.

Rationale: the requirement mandates no shared data between services and fully deterministic,
in-memory behaviour so tests can drive it.

### IV. At-Least-Once, Unordered Delivery Is the Norm
Every handler MUST be idempotent with respect to duplicate events and MUST tolerate events
arriving in any order. Processing the same event twice MUST NOT change state or emit additional
events a second time. Scenarios MUST explicitly cover duplicates and out-of-order arrival for
every event the service consumes.

Rationale: requirement item 8 makes this a correctness property, not an edge case.

### V. Simplicity and Integer Arithmetic
All amounts and quantities are integers; the service MUST reject non-integer or non-positive
quantities/amounts at `placeOrder`. Implementation stays in a single file (`src/order.ts`) with
plain data structures (`Map`) and no external runtime dependencies. YAGNI: no abstraction that is
not required by a scenario.

Rationale: the deliverable is one file that a human integrator must read and trust.

## Technology Stack & Team Boundaries

- Language: TypeScript (strict, ES2022, NodeNext modules). Type check: `npm run typecheck`.
- Test runner: cucumber-js (`@cucumber/cucumber` 11) via `npm test` (tsx loader).
  Feature files live under `tests/features/**/*.feature`; step definitions under
  `tests/steps/**/*.ts`; support code under `tests/support/**/*.ts`.
- Product code lives in `src/`. This engineer MAY modify only `src/order.ts` and files under
  `tests/`. `src/events.ts`, `src/shop.ts`, `src/index.ts`, `src/inventory.ts`, `src/payment.ts`
  MUST NOT be touched.
- Tests for the order service MUST construct the events that the inventory and payment services
  would send (they are stubs during development) and MUST NOT depend on those stubs working.
- No Python, no database, no network.

## Development Workflow & Quality Gates

- Flow: constitution → specify → clarify → plan → tasks → implement → converge.
- Open questions about business behaviour MUST be raised to the requirement owner, never
  answered by guessing; technical-environment questions are resolved from the project itself.
- Gates before "done": `npm run typecheck` clean; `npm test` runs the order-service feature
  files and reports 0 failed, 0 undefined, 0 pending steps; no file outside the allowed set
  is modified (`git status` reviewed).
- Each scenario maps to a requirement item or a clarified decision; the mapping is recorded in
  the spec.

## Governance

This constitution supersedes any other practice in this repository for the order service.
Amendments require: a written rationale in the Sync Impact Report, a semantic version bump
(MAJOR for removing/redefining a principle, MINOR for adding or materially expanding one, PATCH
for clarifications), and an updated `Last Amended` date. Every plan and task list MUST include a
Constitution Check that verifies Principles I–V; a violation MUST be justified in the plan's
Complexity Tracking table or removed.
