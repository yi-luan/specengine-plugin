# Feature Specification: 付款服務（事件驅動下單流程）

**Feature Branch**: `001-payment-service`

**Created**: 2026-11-01

**Status**: Draft

**Input**: User description: 事件驅動下單流程（訂單、庫存、付款三個服務）團隊版需求。本功能範圍僅為「付款服務」：收到 `StockReserved` 後向顧客扣款，發出 `PaymentSucceeded` 或 `PaymentFailed`；收到 `OrderCancelled` 時退還已扣的款項並發出 `PaymentRefunded`。服務之間不共用資料，只透過事件溝通；事件至少送達一次、可能重複、且不保證先後順序；所有金額皆為整數；全部在記憶體中運作，不接觸資料庫或網路。

## Clarifications

### Session 2026-11-01

- Q: 「庫存已保留」先於「訂單已建立」抵達時，付款服務如何處理？ → A: 暫存該事件，等「訂單已建立」到達後再扣款（需求方授權由工程判斷，採此選項以避免誤判付款失敗）
- Q: 訂單已取消後才收到「庫存已保留」，是否扣款？ → A: 不扣款、不發出任何事件；付款服務記住該訂單已取消

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 庫存保留後成功扣款 (Priority: P1)

顧客下單後，庫存已為該訂單保留商品。付款服務向顧客扣款：若顧客餘額足夠，扣除訂單金額並通知訂單已付款成功。

**Why this priority**: 這是下單流程的主要成功路徑，沒有它訂單無法被確認。

**Independent Test**: 在只有付款服務運作的情況下，先告知服務該訂單的顧客與金額，再送入「庫存已保留」事件，即可驗證餘額變化與付款成功事件。

**Acceptance Scenarios**:

1. **Given** 顧客餘額為 1000，且已知訂單金額為 300，**When** 收到該訂單的「庫存已保留」事件，**Then** 顧客餘額變為 700，並發出「付款成功」事件（含訂單編號與金額 300）。
2. **Given** 顧客餘額恰好等於訂單金額 300，**When** 收到該訂單的「庫存已保留」事件，**Then** 扣款成功，餘額變為 0。

---

### User Story 2 - 餘額不足時付款失敗 (Priority: P1)

顧客餘額不足以支付訂單金額時，付款服務不扣款，並通知付款失敗，讓訂單服務與庫存服務能後續處理。

**Why this priority**: 與 User Story 1 同等重要，是下單流程的主要失敗路徑，會觸發庫存放回。

**Independent Test**: 設定顧客餘額小於訂單金額，送入「庫存已保留」事件，驗證餘額不變且發出付款失敗事件。

**Acceptance Scenarios**:

1. **Given** 顧客餘額為 200，且已知訂單金額為 300，**When** 收到該訂單的「庫存已保留」事件，**Then** 顧客餘額仍為 200，並發出「付款失敗」事件（含訂單編號）。

---

### User Story 3 - 取消訂單時退還已扣款項 (Priority: P2)

顧客取消已付款的訂單時，付款服務把已扣的金額退回顧客餘額，並發出退款事件。未曾扣款的訂單取消時不產生退款。

**Why this priority**: 退款是取消流程的必要部分，但取消流程相對於主要下單流程屬於次要路徑。

**Independent Test**: 先完成一筆扣款，再送入該訂單的「訂單已取消」事件，驗證餘額回復且發出退款事件。

**Acceptance Scenarios**:

1. **Given** 顧客已因訂單 A 被扣款 300（餘額由 1000 變為 700），**When** 收到訂單 A 的「訂單已取消」事件，**Then** 顧客餘額回到 1000，並發出「已退款」事件（含訂單編號與金額 300）。
2. **Given** 訂單 B 尚未扣款（例如付款失敗），**When** 收到訂單 B 的「訂單已取消」事件，**Then** 顧客餘額不變，且不發出退款事件。

---

### User Story 4 - 重複與亂序事件不造成重複扣款或退款 (Priority: P2)

事件傳遞可能重複、也不保證先後順序。付款服務對同一事件重複收到時，結果必須與只收到一次相同；同一訂單的扣款與退款各自只發生一次。

**Why this priority**: 這是正確性的核心保證，直接影響顧客金錢，但依附於 User Story 1 至 3 的行為。

**Independent Test**: 對同一個「庫存已保留」或「訂單已取消」事件重複送入多次，驗證餘額變動只發生一次。

**Acceptance Scenarios**:

1. **Given** 訂單 A 已扣款，**When** 相同的「庫存已保留」事件再次送達，**Then** 顧客餘額不再減少，且不再發出新的付款事件。
2. **Given** 訂單 A 已退款，**When** 相同的「訂單已取消」事件再次送達，**Then** 顧客餘額不再增加，且不再發出新的退款事件。
3. **Given** 尚未收到訂單 C 的「訂單已建立」，**When** 收到訂單 C 的「庫存已保留」，**Then** 付款服務暫存該事件、不扣款、不發出任何事件；之後收到「訂單已建立」時才依餘額完成扣款或付款失敗判定。
4. **Given** 訂單 D 已被取消（不論取消事件是否先於「訂單已建立」到達），**When** 收到訂單 D 的「庫存已保留」，**Then** 不扣款，且不發出任何事件。

---

### Edge Cases

- 「庫存已保留」事件比「訂單已建立」事件先抵達時，付款服務尚不知道該訂單的顧客與金額。[NEEDS CLARIFICATION: 事件可能亂序，若「庫存已保留」先於「訂單已建立」抵達，付款服務應該如何處理？選項：(A) 暫存該事件，等訂單資訊到達後再扣款；(B) 直接發出付款失敗；(C) 忽略此事件，依賴事件重送]
- 「庫存已保留」事件比「訂單已建立」先抵達時，付款服務暫存該事件，待「訂單已建立」到達後再處理（見 Clarifications）。若在此之前已收到該訂單的取消，暫存的事件作廢，不扣款。
- 訂單已被取消之後，才收到該訂單的「庫存已保留」事件時，不扣款、不發出任何事件（見 Clarifications）。
- 付款失敗後，該訂單不會自動重試扣款；顧客之後補足餘額也不會觸發扣款。
- 同一顧客同時有多筆訂單時，餘額為共用，每筆扣款與退款各自獨立計算。
- 扣款與退款金額皆為整數；餘額永遠不會因付款服務而變成負數。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 付款服務 MUST 接收「訂單已建立」事件，並記住該訂單的顧客與金額，供後續扣款與退款使用。
- **FR-002**: 收到某訂單的「庫存已保留」事件，且該訂單的顧客餘額大於或等於訂單金額時，付款服務 MUST 扣除該金額並發出「付款成功」事件（含訂單編號與金額）。
- **FR-003**: 收到某訂單的「庫存已保留」事件，且顧客餘額小於訂單金額時，付款服務 MUST 不扣款，並發出「付款失敗」事件（含訂單編號）。
- **FR-004**: 收到某訂單的「訂單已取消」事件，且該訂單曾經扣款成功、尚未退款時，付款服務 MUST 把全額退還給顧客餘額，並發出「已退款」事件（含訂單編號與金額）。
- **FR-005**: 收到「訂單已取消」事件，且該訂單未曾扣款成功時，付款服務 MUST NOT 變更餘額，也 MUST NOT 發出退款事件。
- **FR-006**: 同一訂單的扣款 MUST 最多發生一次，退款 MUST 最多發生一次；重複收到相同事件 MUST NOT 造成額外的餘額變動或事件。
- **FR-007**: 付款服務 MUST 容忍事件亂序抵達：「庫存已保留」先於「訂單已建立」抵達時 MUST 暫存，待訂單資訊到達後再處理；取消事件先於其他事件抵達時，後續同一訂單的扣款 MUST NOT 發生。
- **FR-008**: 付款服務 MUST 忽略與付款無關的事件（例如庫存拒絕、庫存釋放、訂單付款結果等），對其回傳空結果。
- **FR-009**: 付款服務 MUST 只保存自己需要的狀態（顧客餘額與付款紀錄），MUST NOT 讀取或依賴其他服務的內部狀態。
- **FR-010**: 付款服務 MUST 提供查詢顧客目前餘額的能力。
- **FR-011**: 所有金額與餘額 MUST 為整數。
- **FR-012**: 付款服務 MUST 在初始化時接收每位顧客的初始餘額。
- **FR-013**: 付款服務 MUST 為自己產生的每個事件分配全系統內唯一的事件編號。
- **FR-014**: 付款服務 MUST 記住已被取消的訂單；收到已取消訂單的「庫存已保留」時 MUST NOT 扣款，也 MUST NOT 發出任何事件。
- **FR-015**: 付款服務 MUST 暫存「庫存已保留」事件直到該訂單的「訂單已建立」到達；若暫存期間該訂單已取消，暫存事件 MUST 作廢。

### Key Entities *(include if feature involves data)*

- **顧客餘額**：每位顧客一個可用餘額（整數），由扣款增加或減少、由退款回補。
- **付款紀錄**：每筆訂單一筆，包含訂單編號、顧客、金額與付款狀態（等待訂單資訊、未扣款、已扣款、扣款失敗、已退款、已取消）。付款狀態決定該訂單能否扣款或退款。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 對任何一筆訂單，不論「庫存已保留」事件被送達一次或多次，顧客餘額的扣減恰好發生一次（或在餘額不足時完全不發生）。
- **SC-002**: 對任何一筆已扣款的訂單，「訂單已取消」事件被送達一次或多次，顧客餘額的退還恰好發生一次。
- **SC-003**: 所有餘額不足、扣款成功、退款與無退款的情境，在自動化驗證中 100% 通過。
- **SC-004**: 付款服務在收到任何事件後，其產生的事件與餘額結果都可預期且可重現，不依賴事件到達的實際時間或順序（在已裁示的亂序處理方式之下）。

## Assumptions

- 訂單金額與顧客資訊由「訂單已建立」事件提供，付款服務不自行計算金額。
- 輸入的訂單金額為正整數，由訂單服務負責驗證；付款服務不另行處理負數或零的情況。
- 付款失敗後不重試，也不提供人工補扣款的流程（超出本功能範圍）。
- 退款一律為全額退還，不做部分退款。
- 初始餘額由建立服務時傳入，不在本功能範圍內維護顧客的增減值以外的帳務。
- 庫存服務、訂單服務與事件匯流排由其他人員負責，本功能只涵蓋付款服務的行為與其事件合約。
- 本功能不接觸資料庫或網路，全部在記憶體中運作。
