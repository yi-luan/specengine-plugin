# Feature Specification: 會員點數折抵

**Feature Branch**: `001-member-points-discount`

**Created**: 2026-10-20

**Status**: Draft

**Input**: User description: "會員結帳時可以用點數折抵現金，1 點折抵 1 元，折抵點數必須是整數。單筆訂單的折抵金額不得超過訂單金額的 30%。折抵成功後，會員的點數餘額要扣掉這次使用的點數。折抵成功時回傳折抵後的應付金額與剩餘點數；不成功時回傳失敗原因。技術介面固定：`src/points.ts` 匯出 `PointsDiscountInput`、`PointsDiscountResult`、`applyPointsDiscount`，純函式，不碰資料庫，金額與點數皆以整數元／整數點計算。"

## Clarifications

### Session 2026-10-20

- Q: 當折抵點數超過會員點數餘額時，回傳的失敗原因應該是什麼？ → A: 整筆拒絕，不自動折到餘額用完；reason 固定為 `INSUFFICIENT_POINTS`。
- Q: 當折抵點數是負數或非整數（例如 -10 或 10.5）時，回傳的失敗原因應該是什麼？ → A: 拒絕，reason 固定為 `INVALID_POINTS`。
- Q: 當訂單金額為 0 或負數、或會員點數餘額為負數時，系統應該怎麼處理？ → A: 拒絕，reason 固定為 `INVALID_INPUT`。
- Q: 當一次折抵請求同時違反多條規則時，應回報哪一個失敗原因？ → A: 檢查順序固定：`INVALID_INPUT` → `INVALID_POINTS` → `INSUFFICIENT_POINTS` → `EXCEEDS_LIMIT`，回報第一個命中的。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 會員用點數折抵結帳金額 (Priority: P1)

會員在結帳時指定要使用的點數，系統以「1 點折抵 1 元」計算折抵後的應付金額，並從會員點數餘額扣除本次使用的點數，回傳折抵後應付金額與剩餘點數。

**Why this priority**: 這是功能的核心價值——沒有這條路徑，點數折抵就不存在。

**Independent Test**: 給定一筆訂單金額、一個足夠的點數餘額與一個合法的折抵點數，呼叫折抵後能得到正確的應付金額與剩餘點數，即可獨立驗證。

**Acceptance Scenarios**:

1. **Given** 訂單金額 1000 元、點數餘額 500 點，**When** 會員使用 200 點折抵，**Then** 折抵成功，應付金額為 800 元，剩餘點數為 300 點。
2. **Given** 訂單金額 1000 元、點數餘額 300 點，**When** 會員使用 300 點折抵（剛好用完餘額且未超過 30%），**Then** 折抵成功，應付金額為 700 元，剩餘點數為 0 點。
3. **Given** 訂單金額 1000 元、點數餘額 500 點，**When** 會員使用 300 點折抵（剛好等於訂單金額的 30%），**Then** 折抵成功，應付金額為 700 元，剩餘點數為 200 點。

---

### User Story 2 - 折抵金額受單筆訂單 30% 上限保護 (Priority: P2)

單筆訂單的折抵金額不得超過訂單金額的 30%。當會員指定的點數換算後超過上限時，系統不得讓折抵超過上限。

**Why this priority**: 這是保護營收的核心業務規則，缺少它會造成財務損失；但它建立在 P1 的折抵路徑之上。

**Independent Test**: 給定一筆訂單與超過 30% 的折抵點數，驗證系統回應符合上限規則，即可獨立驗證。

**Acceptance Scenarios**:

1. **Given** 訂單金額 1000 元、點數餘額 1000 點，**When** 會員使用 301 點折抵（超過 30% 上限 300 點），**Then** 折抵失敗，整筆拒絕（不自動截斷到上限），失敗原因固定為 `EXCEEDS_LIMIT`。
2. **Given** 訂單金額 101 元（30% 為 30.3 元）、點數餘額 100 點，**When** 會員使用 30 點折抵，**Then** 折抵成功；使用 31 點時 **Then** 折抵失敗，失敗原因為 `EXCEEDS_LIMIT`（30% 上限換算為非整數時採無條件捨去，上限為 30 點）。

---

### User Story 3 - 無效的折抵請求被拒絕並回傳原因 (Priority: P3)

當會員的折抵請求不合法（點數不是整數、點數為負數、點數超過餘額等）時，系統不做任何折抵，回傳明確的失敗原因，且點數餘額不變。

**Why this priority**: 保護資料正確性與使用者體驗；屬於防禦性規則，可在 P1 之後補上。

**Independent Test**: 分別給定非整數點數、負數點數、超過餘額的點數，驗證都得到失敗結果與原因，即可獨立驗證。

**Acceptance Scenarios**:

1. **Given** 訂單金額 1000 元、點數餘額 500 點，**When** 會員使用 600 點折抵（超過餘額），**Then** 折抵失敗，整筆拒絕（不自動折到餘額用完），失敗原因固定為 `INSUFFICIENT_POINTS`。
2. **Given** 訂單金額 1000 元、點數餘額 500 點，**When** 會員使用 10.5 點折抵（非整數），**Then** 折抵失敗，失敗原因固定為 `INVALID_POINTS`。
3. **Given** 訂單金額 1000 元、點數餘額 500 點，**When** 會員使用 -10 點折抵（負數），**Then** 折抵失敗，失敗原因固定為 `INVALID_POINTS`。
4. **Given** 訂單金額 1000 元、點數餘額 500 點，**When** 會員使用 0 點折抵，**Then** 折抵成功，應付金額等於訂單金額（1000 元），剩餘點數等於原餘額（500 點）。
5. **Given** 訂單金額 0 元或 -100 元、點數餘額 500 點，**When** 會員使用 10 點折抵，**Then** 折抵失敗，失敗原因固定為 `INVALID_INPUT`。
6. **Given** 訂單金額 1000 元、點數餘額 -5 點，**When** 會員使用 10 點折抵，**Then** 折抵失敗，失敗原因固定為 `INVALID_INPUT`。

---

### Edge Cases

- 折抵點數剛好等於 30% 上限（例如 1000 元用 300 點）：視為未超過上限，應成功。
- 折抵點數剛好等於全部餘額：應成功，剩餘點數為 0。
- 訂單金額的 30% 不是整數（例如 101 元）：上限採無條件捨去取整數（30 點）。
- 折抵點數為 0：視為成功，應付金額等於訂單金額、剩餘點數等於原餘額。
- 折抵點數為非整數（10.5）、負數（-10）：拒絕，原因為 `INVALID_POINTS`。
- 訂單金額為 0 或負數、或點數餘額為負數：拒絕，原因為 `INVALID_INPUT`。
- 折抵點數同時違反多條規則（例如既超過餘額又超過 30%）：依固定檢查順序 `INVALID_INPUT` → `INVALID_POINTS` → `INSUFFICIENT_POINTS` → `EXCEEDS_LIMIT` 回報第一個命中的原因（例：1000 元、餘額 500、用 600 點 → `INSUFFICIENT_POINTS`）。
- 失敗時不得改變會員點數餘額（純函式不會副作用，但回傳結果中不包含「剩餘點數」的變動）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統 MUST 以「1 點折抵 1 元」的固定比率計算折抵金額。
- **FR-002**: 系統 MUST 只接受整數的折抵點數；非整數的折抵點數 MUST 被拒絕並回傳固定原因 `INVALID_POINTS`。折抵點數為 0 MUST 視為成功，應付金額等於訂單金額、剩餘點數等於原餘額。
- **FR-003**: 系統 MUST 拒絕負數的折抵點數並回傳固定原因 `INVALID_POINTS`。
- **FR-004**: 系統 MUST 確保折抵點數不超過會員目前的點數餘額；超過時 MUST 整筆拒絕（不自動折到餘額用完）並回傳固定原因 `INSUFFICIENT_POINTS`。
- **FR-005**: 系統 MUST 確保單筆訂單的折抵金額不超過訂單金額的 30%；上限為「訂單金額 × 30%」無條件捨去後的整數；折抵點數剛好等於上限視為允許；超過上限時 MUST 整筆拒絕（不自動截斷）並回傳固定原因 `EXCEEDS_LIMIT`。
- **FR-006**: 折抵成功時，系統 MUST 回傳折抵後的應付金額（訂單金額減去折抵金額）與剩餘點數（原餘額減去本次使用點數）。
- **FR-007**: 折抵不成功時，系統 MUST 回傳固定的失敗原因代碼（`INVALID_INPUT`、`INVALID_POINTS`、`INSUFFICIENT_POINTS`、`EXCEEDS_LIMIT` 之一），且不回傳任何折抵後的金額或餘額。
- **FR-008**: 所有金額與點數 MUST 以整數元／整數點計算，回傳值不得出現小數。
- **FR-009**: 折抵計算 MUST 是無副作用的純計算：不存取資料庫、不依賴外部狀態；呼叫方以回傳的剩餘點數更新會員餘額。
- **FR-010**: 訂單金額為 0 或負數、或點數餘額為負數時，系統 MUST 拒絕並回傳固定原因 `INVALID_INPUT`。
- **FR-011**: 多條規則同時違反時，系統 MUST 依固定順序 `INVALID_INPUT` → `INVALID_POINTS` → `INSUFFICIENT_POINTS` → `EXCEEDS_LIMIT` 檢查，並只回報第一個命中的原因。

### Key Entities *(include if feature involves data)*

- **折抵請求（PointsDiscountInput）**：一次結帳的折抵輸入，包含訂單金額（整數元）、會員目前點數餘額（整數點）、會員想使用的點數（整數點）。
- **折抵結果（PointsDiscountResult）**：成功時包含折抵後應付金額（整數元）與剩餘點數（整數點）；失敗時包含固定的失敗原因代碼。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 對任何合法的折抵請求，回傳的應付金額恆等於「訂單金額 − 使用點數」，剩餘點數恆等於「原餘額 − 使用點數」，100% 正確。
- **SC-002**: 任何會導致折抵金額超過訂單金額 30% 的請求，100% 不會以超過上限的折抵金額成功。
- **SC-003**: 任何非整數、負數或超過餘額的折抵點數，以及不合法的訂單金額／餘額，100% 被拒絕並附有四個固定原因代碼之一。
- **SC-004**: 每一條功能需求（FR-001 至 FR-011）至少對應一個可自動執行的驗收情境，且全部通過。

## Assumptions

- 訂單金額與點數餘額由呼叫方提供；訂單金額必須為正整數、點數餘額必須為非負整數，否則依 FR-010 拒絕。本功能不負責查詢或更新會員資料。
- 檢查順序已由需求方確認（見 FR-011），不再是假設。
- 失敗原因為固定英文代碼（見 FR-007）；由呼叫方負責轉成顯示給使用者的文字。
- 「1 點折抵 1 元」的比率固定，不隨會員等級或活動改變。
- 本功能只處理單筆訂單的一次折抵計算，不處理多次折抵或退款回補點數。
