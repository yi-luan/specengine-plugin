# 釐清問題
伺服器可能處理到一半就當機不再回來。最關鍵的空窗是：系統已在共用儲存扣掉了剩餘件數，但還沒來得及寫入保留紀錄就當機。這些件數沒有任何保留指向它們，排程也找不到東西可釋放。以現有的 Store 原子操作（單一 key 的 set/incr/集合增刪），無法同時保證「絕不超賣」與「這類件數一定能回收」，必須二選一。

# 定位
R-FLASH_SALE-012、flash_sales.remaining、holds；模組 FLASH_SALE

# 多選題選項
| 選項 | 描述 (工程 Trade-off) |
|---|---|
| A | 寧可少賣、絕不超賣：這類件數視為遺失，不另做回收。實作以「先扣件再寫保留」保證任何時候成功保留總和不超過限量。極端當機情況下實際賣出可能略少於限量。 |
| B | 必須回收：到期後由排程把這類件數加回。但因為無法分辨「扣件前當機」與「扣件後當機」，極端情況下可能多加回件數而超賣，與「絕對不能超賣」衝突。 |
| Short | 自訂簡答 (<=5 字) |

# 影響範圍
grab 的寫入順序、sweep 的掃描範圍、當機情境的測試案例

# 最終決策
- **決策選項**：需求方回覆「你決定，照你的最佳判斷」。執行者決定（需求方授權）：A。寧可少賣、絕不超賣：先扣件再寫保留，扣件後寫保留前當機所遺失的件數不回收。理由：需求第 6 條「絕對不能超賣」為硬性約束，選項 B 在現有 Store 原子操作下無法排除超賣。
- **寫回位置**：exclusions X-FLASH_SALE-001（系統無動作：不回收此類件數）；矩陣 R-FLASH_SALE-012 維持（不超賣）；policy-defaults POLICY-005
